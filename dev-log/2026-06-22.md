# 2026-06-22

## Cross-region standby (site B) could not track the tip — root cause + fix

**Symptom.** At 4000 TPS the cross-region backup site (B, us-east-2) fell tens of
thousands of blocks behind active site A (us-east-1) and never recovered under load.
Easy to dismiss as generic "cross-region lag"; it is not — it is a specific consensus
throughput limit.

**Evidence (consensus dashboard, `avalanche-consensus`).**
- B's block ACCEPTANCE pinned at ~41-45 blk/s while A produced ~88-160 blk/s.
- B was NOT gas/throughput bound: at 500/1000 rps it executed only ~225/~450 of the
  4000 tx/s — ~10% of capacity, with the rest idle.
- Block production is decoupled from tx rate: A produced ~99 blk/s at 200, 500 AND
  1000 rps alike (proposer mints a block every ~10ms whenever any tx is pending, so
  lower rps just means fewer tx per block, not fewer blocks).
- Therefore throttling rps does NOT help — measured keep-up ratio ~0.44 at every rps,
  gap still growing at 200 rps. B is BLOCK-COUNT bound, and block count is set by the
  block cadence, not by load.

**Root cause (grounded in avalanchego v1.13.3-rc.2).** Snowman does not accept a block
by replaying its gas; it accepts it by POLLING. Per block, the engine runs
`sendQuery` (`snow/engine/snowman/engine.go:883`): `Validators.Sample(SubnetID, K)`
samples K validators, sends a Pull/PushQuery, and registers a poll. The block is only
accepted once that poll returns >= AlphaConfidence (15) votes for beta consecutive
rounds, and each round is a network round-trip to the sampled validators. The pipeline
is bounded by `ConcurrentRepolls: 4` (`snow/consensus/snowball/parameters.go:43`;
`engine.go:699`) and `OptimalProcessing: 10` (parameters.go:44; engine.go:648). So a
node's max acceptance rate ~= ConcurrentRepolls / (beta * poll_RTT) — purely
LATENCY-bound and independent of block size. Same-region trackers (m4/m5) poll over a
sub-ms LAN hop and keep up at ~99 blk/s; cross-region B pays ~10-15ms RTT per poll, so
with 4 polls in flight it caps near ~43 blk/s. When production (99/s) outran B's poll
pipeline (43/s), undecided blocks piled up — the `blks_processing` gauge
(`snow/consensus/snowman/metrics.go:91`, `NumProcessing()`) ballooned to ~3000 on B.
(Aside: `sendChits` `engine.go:578` has a queried node reply with its OWN preference, so
a behind node just votes stale — being a validator does not pull it forward.)

**Fix — block cadence, not throughput.** Granite governs cadence via a `MinDelayExcess`
controller steered by `min-delay-target` (chain-config) / `initialMinDelayMS` (genesis),
both 5ms (-> ~10ms blocks). Raised both to 30ms:
- `genesis.json`: `initialMinDelayMS` 5 -> 30 (consensus seed; needs re-run of 02 / new chain).
- `chain-config.json` + `chain-config-rpc.json`: `min-delay-target` 5 -> 30 (per-node build target).

**Result (4000 TPS, 30ms cadence).**

```text
A blk/s:        21.5     (was ~99)
B blk/s:        22.3     (slightly > A -> draining the residual gap)
B/A keep-up:    1.03     (was ~0.44)         <- SYNCED
B processing:   ~4       (was ~1000-3000)
tip gap:        ~7 blk pruning nodes / ~68 blk archive RPC (stable, bounded)
```

Production (~21 blk/s) now sits under B's ~43 blk/s poll ceiling, so B keeps up at FULL
4000 TPS. Throughput is unchanged (gas-bound, ~190 tx in each fat 30ms block). Cost is
finality latency only: ~10ms -> ~30-46ms (block interval + beta poll rounds), still fast.

**Residual gap is the RPO floor.** A cross-region follower is always >= one
propagation+finalization latency behind the producer; that is ~7 blocks ~= ~0.3s at
21.5 blk/s ~= ~1200 txs at 4000 TPS. Cannot reach zero without synchronous replication
(which would force finality >= cross-region RTT — the trade we explicitly rejected).
Slowing cadence shrinks the gap measured in BLOCKS but not in TIME or TRANSACTIONS.
The archive RPC (rpc-2) trails more (~68 blk / ~3s) because unpruned full-state writes
cost it more per block; stable, and it gates nothing.

EXPERIMENT (2026-06-22): bumped `snow-concurrent-repolls` 4 -> 8 (node-config.json) and
restarted only the B followers in place. Gap did NOT change (5-7 blk, ratio 1.0).
`ConcurrentRepolls` is a THROUGHPUT knob (parallel polls), not a LATENCY knob: it only
helps when production exceeds B's acceptance capacity (the old ~99 blk/s regime). At
30ms cadence B sees ~21 blk/s and already has poll headroom, so the gap is latency-
floored: gap ~= Beta * poll_RTT * block_rate ~= 20 * ~15ms * 21 ~= 6-7 blk (matches).
The only levers that shrink THIS gap are lower `Beta` (fewer confirmation rounds, at a
consensus-safety cost) or lower cross-region RTT (geography, fixed) — NOT ConcurrentRepolls.
