- Failover controller intent: deployment prepares deterministic L1 slots, not validator placement. Each benchmark machine should have two prepared slot launchers on disk with fixed flags, ports, configs, plugins, and data paths; the launcher starts whatever staking identity is currently installed in that slot. The controller runs from the dev host, owns all identity placement, and is the only writer of validator staking keys. On controller startup, it kills all managed L1 processes on reachable machines, cleans/initializes slots, installs the desired initial placement, starts slots, then freezes for about 60 seconds before reconciling. For the first demo, do not literally stop/start EC2 instances: implement machine-level intent as controller state. `disable machine-N` kills both managed L1 slot processes on that machine and marks it unavailable so the controller will not restart there; lost validator identities are placed onto spare slots on live machines. `enable machine-N` marks it available, wipes/reinitializes its slot identities as spares, starts them, waits for healthy/synced state, then rebalances validators back if placement improves. Desired story: `1111` across four machines, disable one machine, recover to `22` across two live machines if needed, then enable/rebalance back toward `1111`. Raw `pkill` without disabled state means restart in place. No systemd/autorestart for validator identities outside the controller. Later the implementation behind disable/enable can become real EC2 stop/start or network isolation, but the failover logic should remain machine availability plus slot health plus the invariant that a validator identity is active in only one slot.

- Source diagnosis for horrendous 2/3 latency: AvalancheGo proposerVM post-Durango assigns 5s proposer slots from the full validator set at the P-chain height, not only connected validators. A killed validator can still own slot 0/1/... for new block heights; live validators must wait until a slot assigned to them, so txs accumulate into delayed blocks. This explains ~2.5s P50 and >5s bombard timeouts while the chain remains healthy/progressing. `min-delay-target=5ms` is inner Subnet-EVM block production, not proposerVM slot duration. ProposerVM outer timestamps are truncated and serialized to whole Unix seconds, so a literal 5ms proposer slot is not meaningful without deeper proposerVM timestamp changes; with current encoding the smallest sane slot-duration experiment is likely 1s.
